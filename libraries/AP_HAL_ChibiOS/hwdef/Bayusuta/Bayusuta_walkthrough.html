Bayusuta QuadPlane tri-tiltrotor

Complete build → flash → configure walkthrough for the Bayusuta dual-MCU autopilot. Every parameter name, enum value and default in this document was verified against its AP_GROUPINFO() definition in the ArduPilot source tree; the citation (file:line) follows each item.

Three placeholders remain hardware-dependent and must be resolved before flight: the two IMU rotations and the periph compass rotation are ROTATION_NONE until the PCB layout orientation is known, and the YRRC power-module voltage/current scales need bench calibration (§9.4).

5. Flash with STM32CubeProgrammer

5.1 Getting a connection

MethodFCC (H753)NAVC (F405)

In CubeProgrammer pick ST-LINK (mode Normal, reset Hardware) or USB (the DFU device appears as "STM32 BOOTLOADER") and press Connect.

5.3 Programming sequence (each board)

  • Connect (§5.1).
  • First time only: Full chip erase. On the NAVC this also erases stored parameters (sectors 2–3); the firmware's embedded defaults.parm re-seeds them at boot.
  • Open Erasing & Programming → select the combined hex (arduplane_with_bl.hex / AP_Periph_with_bl.hex). Hex files carry their own addresses — leave the start-address field empty.
  • Enable Verify programming → Start Programming.
  • If you prefer the two-file route (bootloader first, then app):
    1. Tools/bootloaders/Bayusuta_bl.bin @ 0x08000000 (FCC) or Bayusuta-Periph_bl.bin @ 0x08000000 (NAVC)
    2. arduplane.bin @ 0x08020000 (FCC) or AP_Periph.bin @ 0x08010000 (NAVC)
  • Disconnect; if you used DFU, return BOOT0 to the flash position; power-cycle. Bootloader activity LED: FCC = red LED_A (PD4), NAVC = LED_A (PC3).

5.4 Everyday updates (no CubeProgrammer)

  • FCC: upload arduplane.apj over USB with Mission Planner / QGC, or copy arduplane.abin → SD root as ardupilot.abin.
  • NAVC: Mission Planner → Setup → Optional Hardware → DroneCAN → select the Bayusuta-Periph node → Update with AP_Periph.apj. The FC forwards the image over the CAN bus (MAVLink→CAN passthrough).

6. First boot & sanity checks

  • FCC enumerates over USB-C; GCS connects at 115200/USB. The banner shows the firmware and board; verify the board ID with the bootloader (or Tools/scripts/uploader.py --identify): expect 7150.
  • Messages tab shows both IMUs (Invensensev3 ICM-42688-P and BMI088) and both baros — no "check storage" or FRAM panic (a FRAM fault halts boot by design; libraries/AP_HAL_ChibiOS/Storage.cpp — HAL_WITH_RAMTRON without fallback).
  • Mission Planner → DroneCAN (MAVLink-CAN1): the Bayusuta-Periph node appears with a dynamically-allocated node ID (periph CAN_NODE default 0 = DNA).
  • After §9 params: GPS state healthy, compass present (DroneCAN IIS2MDC), SHT31 temperature visible as DroneCAN device temperature (1 Hz).
  • No airspeed sensor is fitted on this design — nothing to check (ARSPD_TYPE stays default 0:None; value list in libraries/AP_Airspeed param table).
  • Run accelerometer calibration (Mission Planner → Setup → Mandatory → Accel) — only after IMU rotations are finalised.
  • Run compass calibration (Onboard Mag Cal). COMPASS_AUTO_ROT = 2 (CheckAndFix) is this board's default, so a wrong periph-side mounting rotation is detected and fixed during calibration. AP_Compass.cpp:550–551 (values 0:Disabled,1:CheckOnly,2:CheckAndFix,3:+45°)

7.3 MIN / MAX / TRIM / REVERSED

Defaults: SERVOx_MIN 1100, SERVOx_MAX 1900, SERVOx_TRIM 1500, SERVOx_REVERSED 0. SRV_Channel.cpp:37, :46, :55, :62

  • Motors (1–3): with DShot, MIN/MAX are ignored for throttle scaling — leave defaults.
  • Surfaces (5–8): set TRIM so surfaces are neutral, then MIN/MAX to the mechanical limits; fix direction with SERVOx_REVERSED in FBWA on the bench.
  • Tilt servos (9–10): vectored-yaw tilts are range (0–1000) outputs (tiltrotor.cpp:139–140). Set MIN/MAX so full range = straight-up ↔ straight-forward + the Q_TILT_YAW_ANGLE overshoot, and match directions with SERVOx_REVERSED.

8. Bidirectional DShot & ESC setup

The hwdef marks TIM4_CH1–CH3 with BIDIR; the build defines HAL_WITH_BIDIR_DSHOT and allocates a dedicated DMA stream (DMA1-stream-0, re-muxed between the output phase and per-channel RPM capture). Pattern cross-referenced from MatekH743-bdshot and CUAV-X7-bdshot.

PD15 (spare, TIM4_CH4) outputs DShot at the same group rate but can never return RPM: the STM32H7 has no TIM4_CH4 DMA request line (modules/ChibiOS/os/hal/ports/STM32/STM32H7xx/stm32_dmamux.h:64–67 — only CH1/CH2/CH3/UP exist). If a 4th motor is ever fitted there, exclude it from the notch's RPM sources.

11. Ground checks before flight

  • Props OFF — motor order & direction: Mission Planner Motor Test: "Motor A/B/C" fire M1 (front right), M2 (front left), M4 (rear). Check each spins the direction of your chosen prop set; fix direction with DShot commands (requires SERVO_DSHOT_ESC ≥ 1) or by ESC configurator.
  • Tilt direction & endpoints: in QSTABILIZE, nacelles vertical; yaw stick right → left nacelle tilts forward / right tilts back. Switch to FBWA → nacelles slew forward at Q_TILT_RATE_DN. Adjust SERVO9/10_MIN/MAX/TRIM/REVERSED.
  • Surface directions: FBWA, tilt the airframe by hand — ailerons and V-tail must counteract the motion; fix with SERVOx_REVERSED.
  • Bench transition dry-run: props off, arm in QSTABILIZE, switch to FBWA and back; watch tilt slew rates and the Q_TRANSITION_MS blend; no errors in Messages.
  • Failsafes: ELRS off → RC failsafe triggers; set battery failsafe voltages after calibrating §9.4; confirm Q_ASSIST_SPEED is deliberately set (§7.1).
  • Arming checks: leave all pre-arm checks enabled; resolve every pre-arm message rather than masking it.
  • Rotations resolved: both IMU ROTATION_* values and the periph compass rotation updated from the final PCB layout, then accel + compass calibration redone.
